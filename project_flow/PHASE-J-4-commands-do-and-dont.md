# Phase J-4: Commands and Practices (Use, Use with Caution, Avoid)

The verdict is **for this project and context**. Very few commands are bad everywhere. "Caution" says when the command
is unsafe and when it is still legitimate.

| Command or practice | Recommended usage | Avoid or caution | Reason |
|---|---|---|---|
| `npm ci` vs `npm install` | `npm ci` in CI, Docker builds and fresh clones. `npm install <pkg>` locally when **changing** dependencies, then commit the lockfile | `npm install` in CI or Dockerfiles | `install` may rewrite the lockfile and pick newer versions inside `^` ranges, so you'd test code no one reviewed. `ci` fails on lockfile mismatch, which is what you want |
| `npm ci --ignore-scripts` | Runtime images (auth does this) and high-trust pipelines | Where a postinstall is required (auth's `prisma generate`): add that step explicitly | Dependency install scripts run with your token and network. This is the most common supply-chain path |
| `npm audit --omit=dev --audit-level=high` in CI | As now: gate on high/critical **prod** advisories | Gating on `moderate` with dev deps (constant red with no fix available, e.g. S-13) | A gate that is always red gets ignored or deleted |
| `prisma migrate deploy` vs `prisma migrate dev` | `deploy` in CI, migrate images, any shared DB. `dev` only on your laptop to **author** a migration | `migrate dev` against a shared/staging/prod DB | `dev` can **reset the database** when it detects drift and prompts interactively. `deploy` only applies committed files |
| `prisma db push` / TypeORM `synchronize: true` / SQLAlchemy `create_all()` (schema sync) | Throwaway prototypes | Any environment with data, and tests that should mirror production | Sync makes the DB match the model with no reviewable history and can drop columns. This project uses migrations everywhere, and tests apply the real migrations (global setups) |
| Editing an applied migration | Never. Write a new forward migration | — | Environments that already applied it never re-run it, so the schemas diverge silently |
| `alembic downgrade base` / `migration:revert` / `node-pg-migrate down` | CI round-trip on an empty DB; local experiments | Production rollback | Production policy here is **forward-only** (runbooks.md §3). A `down` that drops a column deletes data the old code may still need |
| Migrations at service startup | — | Every replica racing to migrate; a failed migration crash-looping the service | One-off `migrate` task before rollout (this project) |
| `terraform plan` | Every change, reviewed by a human; in CI only with read-only creds once AWS exists | Ignoring a plan that shows `destroy`/`replace` (`-/+`) | The plan is the review artifact. The FIFO queue change, for example, shows as replace |
| `terraform apply` | After reviewing **that** plan: `terraform plan -out=tfplan` then `terraform apply tfplan` | `apply` without a saved plan (re-plans; can differ from what you reviewed) | Saved plans apply exactly what was approved |
| `terraform apply -auto-approve` | Disposable targets: Floci in compose's `messaging-init` (as here), ephemeral test accounts | Any real AWS environment, especially from a laptop | No human sees what is destroyed. Legitimate only where everything is recreatable |
| `terraform init -backend=false` | CI validation, `terraform test` | Before `plan`/`apply` on a real env | Without the backend there's no state, so a plan would assume nothing exists |
| `terraform destroy` | Tearing down a personal sandbox | Shared environments; prod has `deletion_protection` (protect_resources) for a reason | Irreversible for data (RDS final snapshot only if configured) |
| `docker build` vs `docker compose build/up` | `docker buildx build --target X` for images (CI, deploy); `compose` for running the multi-service local stack | Using compose in production; using compose files as the source of production config | Compose is a dev orchestrator: no rolling deploy, no IAM, no secrets store, no health-based rollback |
| `docker compose down -v` | Resetting **local** data deliberately | Casually: it deletes `postgres-data`, `mongo-data` and `auth-keys` (all sessions invalid) | Volumes are your local databases |
| `--no-deps` | Restarting one service on 8 GB RAM | Forgetting the migrate job it skips | Run `docker compose --profile apps run --rm <svc>-migrate` after schema changes |
| Unit vs integration tests | Unit for pure logic (`decide.test.ts`, pricing); integration for SQL, locks, messaging (real Postgres + Floci) | Mocking the database for code whose correctness *is* the SQL (reservations, outbox) | A mock tests your belief about Postgres, not Postgres |
| Emulator (Floci) vs real AWS in tests | Floci in CI/local for SNS/SQS semantics, with per-run prefixes and cleanup | Treating Floci as proof of IAM/KMS/quotas/FIFO throughput | Emulators skip auth and policy evaluation. P1-1 (KMS + CloudWatch) is invisible to them |
| Tests against real AWS | A dedicated, disposable test account with budget alarms | Shared dev/staging accounts; your personal account with admin keys | Costs, flakiness, and collateral damage (test cleanup deleting the wrong queue) |
| Destructive tests against shared environments | Never | — | Global setups here `DROP DATABASE … WITH (FORCE)` and `dropDatabase()`. Pointing `TEST_*_URL` at a shared DB would wipe it |
| GitHub-hosted vs self-hosted runners | Hosted (as now): clean VM per job, nothing persists | Self-hosted runners on **public** repos, or shared across trust levels | A PR can run code on a self-hosted machine and leave persistent malware. Self-hosted makes sense for private repos needing GPUs, cache or private network access, made ephemeral |
| Action pinning: SHA vs tag | `uses: actions/checkout@<40-char-sha> # v4.x.y` + Dependabot `github-actions` updates | Floating tags (`@v4`, used everywhere now), and worse, `@main` | Tags can be moved by the action's owner, or by an attacker who compromises it (tj-actions/changed-files, 2025). A SHA is immutable |
| Long-lived AWS keys vs OIDC | OIDC + per-repo, per-environment role (designed here) | `AWS_ACCESS_KEY_ID` secrets in GitHub | Keys leak through logs, forks and laptops, and live until rotated. OIDC creds expire within an hour and are bound to repo + environment |
| Secrets via env vars | Fine for short-lived, masked secrets read by one step | Echoing them, `set -x` in scripts, passing them to steps that don't need them, putting them in `vars` | GitHub masks known secret values in logs, but not transformations (base64, JSON). This project uses **no secrets** in workflows, which is ideal |
| Secrets in images or Terraform | Never; runtime from Secrets Manager (designed) | `ENV STRIPE_KEY=…` in a Dockerfile; secret values in `.tfvars` | Image layers and state files are copied, cached and shared |
| Deploy workflows on every PR | — | Running `deploy*` on `pull_request` | PR code is untrusted; deploys need credentials. This project correctly deploys only from `push: main` / dispatch |
| `workflow_dispatch` on deploy | Re-deploys, hotfix promotion | Without Environment branch rules: anyone with write access can deploy **any branch** to production | Restrict each Environment's deployment branches to `main` |
| Unpinned dependencies in CI (`pip install fastapi`, `npx tool` without version) | Pinned: `pip install -r requirements*.txt` (all `==`), `pipx run pip-audit==2.10.0`, lockfiles | `npx <tool>` without a version (downloads latest at run time) | Reproducibility and supply-chain safety |
| `npx <tool>` inside images (`npx prisma migrate deploy`, `npx node-pg-migrate`) | When the tool is in `node_modules` (verified for all here) | When it isn't: `npx` silently downloads from the internet at run time | Same command, very different trust |
| Retrying a payment/refund/message without idempotency | Retry **with the same idempotency key** (saga `{sagaId}:refund`, provider `refund:{refundId}`) | Retrying with a new key; "retry" buttons that create new requests | Without a stable key a timeout retry can double-charge or double-refund. This project propagates keys end to end |
| `git push --force` on `main` | Never | Rewriting published history | Breaks every clone and makes "which commit is deployed" unanswerable |
| `continue-on-error: true` / `|| true` in CI | Non-blocking informational steps, labelled as such | On tests, audits, scans | Hides real failures behind green checks |
| `pull_request_target` | Only for workflows that never check out or run PR code (labelling, comments) | Checking out the PR head in it | It runs with **write token and secrets** in the base repo context. This is the classic "pwn request" |
| `cancel-in-progress: true` | PR CI | Deploy jobs (this project correctly uses `false`) | Cancelling mid-migration or mid-rollout leaves an environment half-changed |
